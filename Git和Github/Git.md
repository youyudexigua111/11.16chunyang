#### 学习目标：
1. Git 是什么？为什么它能够成为广泛使用的版本控制工具？
    Git是本地就能完成管理版本历史的工具，分布式和轻量分支是它广泛使用的根本原因
	#分布式：
		每个开发者本地都有一份完整的仓库，包括全部文件、全部提交历史和全部分支信息，而不只是最新代码
		
	#集中式版本控制：
		历史只存在中央服务器
	
	#轻量分支：
		Git的分支本质上只是一个指向某次提交的指针，创建、切换、删除的成本极低，几乎不复制任何文件。提交时，只有当前分支指针向前移动；切换分支只是切换指针和工作区
2. 为什么开发者需要版本控制？直接复制文件备份有什么局限？
	#版本控制的核心能力：
		回退到任意历史版本、比较差异、追溯谁在何时为什么改
	
	#直接复制文件夹的局限：
		1.分不清最新版，容易覆盖错
		2.多人修改无法可靠合并
		3.没有变更原因和责任人记录
		4.备份集中在同一个设备时有丢失风险
	#Git的分布式克隆本身也是一种完整备份
		分布式克隆：git clone得到的时一个包含完整历史和分支信息的独立仓库副本，而不是只拿到最新文件；每个克隆都能独立完成版本控制操作，远程仓库只是另一个用于协作同步的副本.
3. Git、GitHub 和 Gitee 分别是什么？它们之间有什么区别？
	#Git 
	    版本控制工具，装在本地，负责管理历史
	#GitHub/Gitee
		基于Git的远程代码托管与协作平台
	#区别
		GitHub国际化、开源生态最丰富
		Gitee国内访问快
		Git是引擎，GitHub/Gitee是带网页协作功能的代码托管平台
4. 什么是仓库、提交、分支和合并？
    #仓库
		带完整历史记录的代码数据库，分本地仓库和远程仓库。
    #提交
		一次不可变的项目快照，包含哈希、作者、时间、提交信息。
    #分支
		指向某次提交的可移动指针，用来并行开发不同功能。
    #合并
		把一个分支的改动整合到另一个分支；同一区域冲突需手动解决。	
5. 在团队协作中，如何使用 Git 管理和同步项目文件？
	#核心原则 
		- `main` 分支受保护，不直接写代码，只通过 PR 合并。    
			-通过PR合并：PR = Pull Request（合并请求）
			在平台发起合并请求->队友审查和自动化检查->通过后由平台把分支合入main
	    - 每个任务开独立功能分支。
		- 每天同步主线，分支不要活太久。
	#加入项目时
		1.克隆远程仓库到本地
		2.配置身份信息
		3.确认远程地址
	#日常同步
		**每天开工前的标准动作：**
			git switch main
			git pull origin main          # 主线更新到最新
			git switch feature/xxx        # 回到自己的功能分支
			git rebase origin/main        # 把主线新提交接到自己分支下面
			如果团队不熟悉 rebase，也可以用 `git merge origin/main`，效果是合并而不是变基，历史会多一个合并提交，但更安全直观。
	#功能开发中的提交与推送
		1.从最新主线开分支
		2.小步提交
		3.定期推送到远程（即使没做完）
	#通过PullRequest完成合并
		1. 把分支推到远程；    
	    2. 在 GitHub/Gitee 上创建 **Pull Request（PR）** ；    
	    3. PR 描述写清楚：改了什么、影响范围、如何测试、是否有数据库/配置变更；
	    4. 指定审查人，队友逐行审查并提意见；
	    5. 根据意见修改，继续往同一分支提交，PR 会自动更新；
	    6. 审查通过后合并到 `main`；
	    7. 删除已合并的远程分支，本地切回 `main` 并 `pull` 最新代码。
	#冲突处理
		冲突发生在**两个分支修改了同一文件的同一区域**时。处理原则：
		    1. **先理解，再动手**：看清楚冲突双方各自想表达什么，不要凭感觉选一边；
		    2. **涉及业务逻辑的冲突，找改动另一边的同事确认**；
		    3. 解决后**跑相关测试**，确认没破坏功能；
		    4. 再 `git add` + `git commit` 完成解决

#使用git第一步
	 git init
	init 就是初始化的意思
	把一个文件夹进行git init就是把这个文件夹使用git管理起来 让这个文件夹变成一个git仓库
	.gitignore忽略清单
	该文件声明了仓库里面哪些文件不应该受到git的管理
#commit
	commit 提交
	commit ID 有长短两种 短ID是长ID的前7位 功能一样 commit ID在一个仓库中是绝对唯一的
	discard 行为：放弃掉还没commit的文件更改   场景：文件更改还没有commit
	reset  行为：把仓库强制回退到某个历史状态  场景：单人使用的分支还未提交远端仓库
	revert 行为：通过生成反向commit 抵消某次commit   场景：多人协作的分支
#branch
	branch 分支 存储库的不同开发线
	主干分支：main/master
	特性分支：feature
	创建一个分支的操作通过指针实现 对feature修改并完成commit 后这些修改仅对feature分支有效，在主干上不会被看到，在各自分支上的代码修改不会互相影响
	当功能开发结束 把分支合并会主干的操作称为merge 合并
	当一条分支开发完毕并且合并了代码后一般需要删除这个分支

# 两种把仓库回退到历史的方法
1. 右键Checkout(Detached) 【分离头指针状态】 最好不要修改 容易搞丢代码
2. 基于某个历史提交直接创建分支 可以自由修改

HEAD：当前仓库处于哪一次commit上 （在分离头指针状态时指向历史的提交）

#WorkTree
	git工作树：本质是用Git创建一个新的分支，把新分支的代码完整的复制一份到一个新的文件夹里面，这个新的文件夹就是一个WorkTree 主文件夹和分支文件夹可以并行工作
#Conflict 
	合并冲突：如果两个分支修改了同一个文件的同一行代码 合并的时候Git无法自动确认保留哪个
	此时需要人工解决冲突

#GitAreas 
	git分区：1.working Directory（工作区）电脑上的本地文件夹
	2.local repository（本地仓库）
	3.remote repository（远端仓库）
	4.staging/index（暂存区）
